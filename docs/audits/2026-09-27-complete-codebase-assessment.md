## 1. Executive summary

Aqua is a Next.js/PostgreSQL multi-tenant operating system for Indian sports academies: staff run membership, batches, attendance, enquiries, counter collections, café and facility workflows; owners configure and review the business; operators provision tenants; parents use a signed zero-JavaScript link. The trust design is strong in outline: a session-derived tenant context, action permission checks, scoped service transactions, forced PostgreSQL RLS under a non-owner application role, and a separate privileged migration process. The implementation has consequential exceptions.

**Confirmed on the audited source and disposable PostgreSQL:** a receptionist's enrolment action drops identity/location context and can enrol across locations; a staff attendance mark accepts a same-tenant member outside the session roster; the parent-link action's `members.write` gate also admits receptionists despite its owner/admin-only contract and does not verify the target member/location; a *first* fresh `db:deploy` leaves `app_user` able to UPDATE/DELETE append-only announcements and other restricted tables until a second deploy; and a same-tenant payment-reversal lookup exposes another location's reversal reason/amount. Enrolment and attendance lack transaction-coincident audit records; an import with a conflicting supplied code silently skips a different person. Totals: **Critical 0 / High 4 / Medium 4 / Low 0**. The merge process additionally relies on human discipline: the active ruleset requires zero approving reviews, and its label can be applied by the agent's GitHub identity.

The complete sharded suite covered **316/316 files**. Against a database after **one** fresh deploy it failed (**2,498 passed, 1 failed, 1 skipped**) on the append-only privilege assertion. Against a separate fresh database after **two** deploys it passed (**2,499 passed, 0 failed, 1 skipped**). Both results matter: the second does not invalidate the first. The production build, typecheck, lint, local Docker backup dry-run, local isolated restore, host-boundary and zero-JS probes passed. Real R2 upload/restore, target VPS/Dokploy configuration, actual role journeys, and Production approvals have not been observed.

## 4. Architecture and trust boundaries

`app/` is the Next.js 15 App Router: four staff route groups with server components/layouts, zero-JS `app/p/[token]/route.ts`, public check-in route, and explicitly gated API handlers. `middleware.ts:26-35,36-108,132-165` routes ops versus apex by `Host`; its matcher deliberately excludes `/_next/image`, `/_next/static` and favicon. Any non-`ops.` host is classified apex; the **reverse proxy's accepted host list is a necessary external boundary**. Middleware is host/path reachability, not authentication. Staff auth resolves Better Auth session → active membership/default tenant → role/feature sets and membership locations (`lib/auth/context.ts:67-133`); staff PIN/magic-link endpoints are `app/api/login/pin/route.ts`, `app/api/login-link/redeem/route.ts`, `app/api/account/set-pin/route.ts`, with lockout in `lib/services/pin-lockout.ts`. Ops uses its own TOTP/session/cookie.

Trust flows **untrusted form/ID → Zod + session + `requirePermission` in `lib/actions/**` → service-level resource/role/location check → `withTenant` transaction → PostgreSQL RLS/FKs/unique indexes → same-transaction tenant audit where implemented**. A successful permission check does not grant access to all resources in that tenant. `tests/tier1/server-action-preamble.test.ts` and `tests/action-permission-scan.test.ts` check action shape; they cannot establish row-level authorization. `db/tenant.ts:10-27` validates tenant UUID and sets `app.tenant_id` transaction-locally. `db/client.ts:40-48` logs in as `app_login`, executes `SET ROLE app_user`; `db/bootstrap-roles.ts:22-45` defines NOINHERIT login and blanket app grants. Tenant RLS policies use `nullif(current_setting('app.tenant_id',true),'')::uuid`, FORCE; user-scoped membership resolution uses `withUser` (`db/tenant.ts:30-56`). Privileged migrator/backup URL must never reach web/worker. In non-production an extra query-scope guard runs (`db/client.ts:20-38`), absent in production; actual DB RLS remains the tenant boundary.

`db/migrate.ts` serializes forward-only SQL against `_migrations`; `db/deploy.ts` bootstraps roles, applies 102 migrations, reconciles pg-boss queues/schedules and grants queue access. Crucially, this ordering leaves fresh-table privileges wrong until a **second** bootstrap (H04). `worker/index.ts:69-139` handles eight scheduled per-tenant queues, platform metrics and event ingestion, records a heartbeat and drains on SIGTERM. Business audit is `audit_log`; ops uses `platform_audit_log`; `activity_events` is a separate at-least-once analytics stream, emitted after some commits (`lib/actions/coach.ts:212-241`). These are not interchangeable. Activity/export/checkpoint and backup use Cloudflare R2 via `lib/storage/object-store.ts`; the R2 call is outside the PostgreSQL transaction.

The Docker runtime (`Dockerfile:29-58`) runs non-root `aqua`, includes PG16 tools and only backup-related scripts. Tracked `docker-compose.dokploy.yml` (Dev) and `docker-compose.production.yml` run DB → one-shot migrate → web + one worker, dormant backup profile, named distinct DB volumes, only web attached to external `dokploy-network`; Prod uses image digest, Dev a SHA-shaped tag (`docs/deployment.md:9-49`). `deploy/aqua-backup@.{service,timer}` and `scripts/backup-compose.sh` require **human installation**. `.github/workflows/ci.yml:52-332` runs build, scanners, image dry-run, complete sharded suite and E2Es; `publish.yml:13-51` **rebuilds** from successful main CI's commit and publishes a sha-tag (the published image is not the exact CI-built image). `deploy-dev.yml` SSH path is retired; `deploy-prod.yml` is an approval/handoff, **not an automated deploy**. TLS, accepted hosts, label injection, private registry pull, persisted volume, digest and one-shot recreation are external Dokploy/Traefik responsibilities.

## 6. Data model and invariants

`db/schema/{tenants,locations,users,memberships,roles,staff,staff-locations}.ts`: one tenant → multiple locations; global login identity → tenant membership with role, status, `all_locations` or membership-location grants; default role/permission and feature grants. `db/schema/{people,consent}.ts`: person → member (one membership code per tenant, `db/schema/people.ts:49-90`), optional guardian person + guardianship + immutable processing consent. Tenant-qualified FKs prevent attaching another tenant's person/location. `db/schema/{programs,scheduling}.ts`: program → batch → session; enrolment ties member to batch; session has copied coach/site and unique `(tenant,batch,date)`; attendance references member and session separately and is unique per pair/client ID (`db/schema/scheduling.ts:22-149`). None of these FKs assert enrolment in session's batch. `db/schema/{enquiries,waitlist-entries,makeup-credits,skill-framework,shifts,staff-attendance,leave}.ts` support trials, transfers, assessment and staff operations.

`db/schema/{membership-plans,subscriptions,invoice-numbering,invoices,payments,payment-reversals,receipts,cash-counts,account-entries}.ts`: per-tenant plan/subscription, year-specific invoice numbers, invoice/line items, capture/reversal, immutable PDF, cash-count and café wallet entries. Critical indexes include one active member/plan subscription (`db/migrations/20260915160000_subscriptions_active_member_plan_uidx.sql`), per-tenant/method/reference payment uniqueness (`db/migrations/20260915140000_payments_reference_uniqueness.sql`), and unique receipt `(tenant,payment)` (`db/schema/receipts.ts`). `db/schema/{menu,orders,bookings,activity-types,facility-optins}.ts` link café and facility usage to member/site/invoice. Parent links are **stateless signed tokens**, with issuance in `audit_log`, not rows in an import/link-run table (`lib/services/parent-link.ts`, `lib/actions/parent-link.ts`); import identity and per-row results live in `audit_log.after`, not a dedicated import-runs table (`lib/services/member-import.ts:149-237`). Worker schedules live in pg-boss tables; heartbeat in `worker_heartbeats`; `audit_log` is monthly partitioned through 2028-12 without default partition (`db/migrations/20260918090000_h03_audit_log_partitioning.sql:15-26`); `activity_events`/rollups and `platform_audit_log` are distinct. R2 backup/checkpoint objects are **outside** the relational schema. Tenant tables are FORCE-RLS with tenant-leading indexes in current migrations (`db/migrations/20260918051000_h02_rls_policy_convergence.sql`, `scripts/check-tenant-conventions.ts`); platform-wide tables carry specialized policies/scopes.

## 7. Authorization and isolation assessment

Tenant RLS and tenant-composite FKs were exercised by the complete suite, including `tests/tier1/{isolation,rls-policy-shape,permission-matrix}.test.ts`; fresh isolated restore showed 134 RLS-enabled/forced relations and `app_login/app_user` with `rolbypassrls=false`. This establishes cross-tenant resistance for the tested schema, **not** per-location/roster authorization: RLS intentionally knows only tenant ID. `lib/services/location-access.ts:46-60` returns unrestricted for missing `userId` when location scoping is enabled, assuming a job/system actor. Consequently a normal action that discards user context becomes system-like (H01). Other `{tenantId:ctx.tenantId}` action calls were examined: `lib/actions/{dashboard,owner-reports,owner-analytics}.ts` require financial/owner permissions; `lib/actions/{branding,terminology,staff-invitations}.ts` target tenant-wide data; `lib/actions/people.ts:142-145` gets a tenant identity-card context, not member-by-ID. They are not automatically exploitable location bypasses. `lib/actions/{transfer,people}.ts` sometimes retain user ID and allow the service to fall back to membership lookup; unlike enrolment they do not omit it entirely. Service scan `pnpm check:location-scope` passed but is a source-pattern/allowlist check, not call-graph proof. Another resource lookup lacking location protection is M01.

Parent and premises credentials have distinct models. Parent HMAC scope/expiration is verified in `lib/services/parent-link.ts:75-153`; route reads and receipts use tenant/member ID from verified claims (`app/p/[token]/receipt/[paymentId]/route.ts:15-24`, `lib/services/receipts.ts:50-85`). Parent `claims.personId` is **actually a member ID**, not `persons.id`: tracing `lib/actions/parent-link.ts:61-64` through `lib/services/parent-view.ts:125-137` disproves a tempting false finding that valid receipts always 404. Issuance authorization is nonetheless insufficient (H03). The premises QR is public and by itself not staff authentication; `app/check-in/[token]/page.tsx:29-76` requires staff session, `staff.self`, own-tenant token and staff row. Host boundary E2E passed 19 probes including ops denial and unauthenticated check-in page; production accepted Host/TLS remain proxy-dependent. The action matrix/AST tests do not replace this end-to-end identity/resource analysis.

## 8. Business integrity, concurrency and recovery assessment

**Verified protections:** batch capacity is counted under a row lock; repeated enrolment day uses `ON CONFLICT DO NOTHING`, though a duplicate returns `ok:true` without indicating no new row (`lib/services/register.ts:196-245`). CSV preview is read-only, commit locks tenant row and atomically writes members/guardian/consent/audit; replay uses normalized tenant-bound SHA-256. Missing guardian for minors is a row error; non-attested commit fails. Concurrency, rollback and 500-row boundary are tested (`tests/member-import.test.ts`). Invoice issue snapshots GST, item lines and audit in a caller transaction. Counter payment checks overpayment under invoice lock, enforces reference uniqueness by DB index and audits atomically; reversal locks payment, sums past reversals, adjusts invoice and audits in one transaction. Receipt generation is independent of payment commit; first read uses insert-conflict handling. Targeted five-file money/enrolment suite passed 25 tests. `db/schema/scheduling.ts:42-51,94-102` establishes tenant-coherent member/batch/session relationships, but **not** valid member-to-program/location or roster membership; the latter is H02.

**Limits:** R2 write, pg-boss processing and HTTP response cannot participate in a PostgreSQL transaction. Activity events are enqueued after attendance commit (`lib/actions/coach.ts:212-241`); a failure can produce a saved attendance mark and a failed action response/no analytics event. The strict tenant audit rule is separately violated by M02. Several money call sites convert bigint DB values with `Number` (`lib/services/{payments,payment-reversals,invoice-issue}.ts`): individual payment input capped at 10,000,000,000 paise, but no comprehensive aggregate `Number.MAX_SAFE_INTEGER` proof; no rounding defect reproduced. Tenant-local scheduling and date helpers exist (`lib/time/tz.ts`), while `enrolMember` defaults `enrolledOn` from UTC (`lib/services/register.ts:238`), creating a real IST midnight boundary mismatch for an enrolment created between 00:00 and 05:29 IST. This is Medium finding M04 below, not something `timestamptz` solves for business dates. `tests/tier1/timezone.test.ts` does not establish this enrolment default. Retry/idempotency tests cover individual jobs, not a real two-stack worker overlap or live infrastructure.

## 9. Security assessment

- **Auth/rate limits:** Better Auth staff sessions, PIN route and account lockout; platform password/TOTP separate. `tests/auth/*`, `tests/tier1/{auth-context,platform-auth,magic-link-login}.test.ts` cover meaningful negatives. Actual cookie flags, proxy-forwarded origin, rate-limit persistence under a live VPS and first-login SMS/OTP delivery remain unobserved. `middleware.ts` does not authenticate by itself.
- **CSRF/XSS/SQLi/SSRF/redirects:** server actions use framework request boundaries and Zod/permission gates; direct custom routes need own auth. SQL in examined services uses Drizzle parameters; escaped printable PDF filename (`lib/services/receipts.ts:30-32`); no proven request-path SQLi, SSRF, XSS or open redirect. This is not an exhaustive adversarial fuzz test. Parent URL token is a bearer credential: no revoke store; do not share it. User-supplied CSS/source-map parsing was not found on a request path. ## 14. Findings, ordered by severity

Gate notation below: **L** local UX audit; **D** synthetic, non-live Dev deployment; **P** friend pilot; **R** Production. `block` denotes a minimum gate, `no` means not inherently blocking this gate. All exploit probes used synthetic data; no real account was attacked.

### H01 — Staff enrolment action loses location/actor context — High, confidence High

**Roles/entry:** location-scoped receptionist (or other staff with `members.write`), direct `enrolMemberAction` from member detail or crafted Next-Action. **Path:** authenticated `requireDefaultCtx` + permission (`lib/actions/enrolment.ts:32-39`) → drops `userId/allLocations/locationIds` → `enrolMember` (`lib/services/register.ts:179-245`) → `resolveLocationAccess` returns unrestricted without user (`lib/services/location-access.ts:46-60`) → batch `FOR UPDATE` and same-tenant FK permit B-site enrolment → no audit. **Preconditions:** tenant config `access.location_scoped_staff=true`, caller restricted to A, known B batch ID, any same-tenant member ID. **Impact:** changes another site's roster/capacity; a B-site member is also not checked for the source member's location. **Insufficient protection:** tenant RLS/FKs and `members.write` are not location/relationship authorization. **Reproduction:** disposable DB probe A-scoped context returned `Batch not found`; tenant-only action-shaped context returned `{ok:true}`; existing `tests/location-scoped-access.test.ts:249-253` tests only the former. **Correction:** pass complete authenticated ctx, fail closed on missing actor in staff-facing service, verify member and batch site/program policy inside same transaction; write one actor audit row only when INSERT occurred. **Tests:** direct action with authenticated scoped membership A vs B, cross-tenant IDs, disabled flag, duplicate/concurrent insert and no audit on denial. **Gates:** L no / D no (dummy-only) / P block / R block.

### H02 — Session-visible caller can mark an out-of-roster member present — High, confidence High

**Roles/entry:** coach or staff holding `attendance.mark`, `markAttendanceSessionAction`. **Path:** `lib/actions/coach.ts:194-212` validates/session permission and coach/session visibility only → `lib/services/register.ts:248-295` reads session location and upserts any same-tenant member ID → `db/schema/scheduling.ts:106-148` checks separate tenant FKs, not enrolment → post-commit activity enqueue (`lib/actions/coach.ts:214-241`). **Preconditions:** known visible session and any other same-tenant member ID (not necessarily enrolled); same-tenant FK rejects foreign tenant. **Impact:** false attendance/absence/history/analytics/parent view; no durable actor audit. **Insufficient protection:** session visibility, clientId uniqueness and tenant RLS do not validate the member/session relationship. **Reproduction:** disposable DB B-site session with no enrolments, B member: `markAttendance` created one `present` row, zero tenant audit rows; positive controls for legitimate marks in `tests/tier1/attendance-upsert.test.ts` do not check an ineligible ID. **Correction:** assert eligible batch enrolment effective on session date, membership status and permitted exception (trial/makeup) within the mark transaction, with conflict/re-mark audit. **Tests:** eligible vs non-enrolled, another site, another tenant, cancelled session, effective date, repeat mark and concurrent/retry actor attribution. **Gates:** L no / D no / P block / R block.

### H03 — Parent-link issue action admits receptionists and lacks target resource check — High, confidence High for reachable authorization path

**Roles/entry:** authenticated receptionist via direct Next-Action to `issueParentLinkAction` (the owner layout is not a Server Action guard). **Path:** `lib/actions/parent-link.ts:12-24,41-64` states owner/admin-only but checks only `members.write`; receptionist has that grant (`lib/services/roles.ts:66-83`) → signs an arbitrary caller-provided member UUID before querying any member or location → writes audit (`lib/actions/parent-link.ts:84-115`) → `/p/[token]` verifies HMAC and reads tenant member attendance/money (`lib/services/parent-view.ts:118-137,179-269`), including an out-of-location member. **Preconditions:** valid receptionist session, action hash/endpoint and known same-tenant member ID; no cross-tenant leak established. **Impact:** can mint shareable seven-day child financial/attendance bearer URL outside intended issuer role and own site; invalid IDs still produce misleading issuance audits. **Insufficient protection:** owner layout is bypassable as an action boundary (role-bypass E2E tests this attack shape); token signature protects against forgery, not unauthorized legitimate issuance. **Evidence:** source end-to-end grant and issue path; no signed-in receptionist POST was performed, so classify as proven reachable code path, not an observed real-session exfiltration. Existing parent-link tests emphasize signature/audit but do not assert receptionist direct action denial. **Correction:** require explicit issue permission/role and member existence/location/guardian policy *inside* the audited transaction before signing/returning token. **Tests:** real session/action POST as owner and receptionist, scoped B target, nonexistent/cross-tenant ID, audit and receipt denial. **Gates:** L no / D no / P block / R block.

### H04 — First fresh deploy grants app role UPDATE/DELETE on append-only tables — High, confidence High

**Roles/entry:** anyone obtaining normal app-role SQL execution through an authorization flaw, future buggy service, or compromised application process; not a demonstrated unauthenticated HTTP endpoint. **Path:** one-shot `db/deploy.ts:174-179` runs `bootstrapRoles` **before** new migrations; `db/bootstrap-roles.ts:42-100` attempts REVOKE only on tables already present → later `20260918125000_u06_announcements.sql:29-95` creates tables with broad default privileges (`db/bootstrap-roles.ts:110-113`) → first deployment app_user has announcements UPDATE/DELETE, notifications DELETE (and analogous append-only tables). RLS still confines tenant data; the intended append-only hard boundary is missing. **Precondition:** genuinely fresh database and exactly one deployment; repeat deploy revokes. **Impact:** app-role SQL can rewrite/delete announcement/delivery evidence and other append-only tenant rows in its RLS scope; compliance/integrity hardening is absent in first deployment. **Insufficient protection:** migration's narrow `GRANT SELECT,INSERT` does not cancel default broad grant; CI reset+deploy bootstraps twice. **Reproduction:** new DB #1 full test **failed** `tests/tier1/announcements.test.ts:234-254`; new DB #2 privilege query immediately after first deploy `t|t|t`, after second `f|f|f` and suite passed. **Correction:** bootstrap/revoke after migrations as part of every deploy, with transactional/DDL-safe sequencing, or add new forward migration revoking exact append-only grants; review all partitions/default privileges. **Tests:** fresh database, **single** real `db:deploy` then app_role privilege and prohibited mutation probes; existing second-run idempotency proof retained. **Gates:** L no / D no (synthetic rehearsal can expose it) / P block / R block.

### M01 — Reversal list bypasses location-scoped financial read — Medium, confidence High

**Roles/entry:** location-scoped accountant/owner/admin with `payments.read`, direct `listPaymentReversalsAction(paymentId)` (`lib/actions/payment-reversals.ts:42-49`). **Path:** session + permission → `lib/services/payment-reversals.ts:174-200` takes only `Pick<ActionCtx,"tenantId">`, selects reversals solely by tenant/payment ID → RLS admits another location's payment reasons/amounts. **Preconditions:** location-scoped staff with payment-read permission and known payment ID in same tenant; no cross-tenant bypass. **Impact:** disclosure of internal finance correction reason/amount across sites. **Insufficient protection:** `reversePayment` mutation itself checks site (`:47-61`), but list does not; tenant RLS is coarser. **Reproduction:** disposable tenant with A-scoped context and B-site payment/reversal returned B's reason and 500 paise. **Correction:** accept full ctx, join payment/location and constrain by resolved location access before returning; keep empty response for missing/foreign. **Tests:** direct action with scoped accountant, A/B payment ID, tenant B and owner all-locations positive control. **Gates:** L no / D no / P block if scoped finance role enabled, otherwise decision required / R block.

### M02 — Enrolment and attendance do not audit in the write transaction — Medium, confidence High

**Roles/entry:** member enrolment or coach attendance actions; same paths as H01/H02. **Path:** `lib/services/register.ts:238-245,277-295` writes enrolments/attendance and commits with no `auditLog`/`writeAudit`; attendance's `emitActivityEvents` happens **after** commit (`lib/actions/coach.ts:212-241`). **Preconditions:** legitimate write; no attacker needed. **Impact:** missing immutable who/what history and activity enqueue can fail after a successful DB mutation; `attendance.markedBy` is defined (`db/schema/scheduling.ts:121`) but not set in the upsert. **Insufficient protection:** unique rows and separate activity stream; `tests/tier1/tenant-audit-coverage.test.ts:53-87` only pins enumerated sites, excluding these. **Reproduction:** disposable enrollment + attendance probe had zero tenant audit rows; full suite passes after double deploy. **Correction:** record actor/old-new/status in same `withTenant` transaction, audit only effective writes, carry `markedBy`; choose reliable activity outbox/reconciliation if analytics must not miss events. **Tests:** successful and replay/no-op, failed and rolled-back writes, concurrent marks, actor, intentionally failed audit insert causing entire mutation to roll back. **Gates:** L no / D no / P block / R block.

### M03 — Supplied CSV member code silently absorbs another person's row — Medium, confidence High

**Roles/entry:** owner import commit `lib/actions/member-import.ts:58-81`. **Path:** permission/attestation → file-atomic `lib/services/member-import.ts:137-245` → `lib/services/member-import-match.ts:18-23` matches existing code without comparing name, DOB, phone or site → result `skipped` and `errors:[]`, import audit records that skip. **Preconditions:** CSV row names a different person with a code already assigned in same tenant and visible scope. **Impact:** that person is never imported and operator sees an apparently clean skip; not a duplicate-creation or cross-tenant defect. **Insufficient protection:** code uniqueness and import hash prevent duplicates but do not establish identity. **Reproduction:** disposable import of `Entirely Different,1980-01-01` with existing `PROBE-A` → `{imported:0,skipped:1,errors:[]}`; test `tests/member-import.test.ts:391-407` *expects* this behaviour. **Correction:** classify mismatched identity as row-level conflict requiring operator reconciliation; design normalization/guardian matching explicitly and preserve file identity/audit replay semantics. **Tests:** same-code/same-person replay, same-code/different-person, within-file conflict, DOB/phone normalization, minor guardian ambiguity, partial accepted/errored file and interruption retry. **Gates:** L no / D no / P block for migration-based pilot / R block.

### M04 — UTC enrolment default dates a local early-morning admission as yesterday — Medium, confidence High

**Roles/entry:** owner/reception enrolment action or system caller with no explicit `enrolledOn`; `lib/actions/enrolment.ts:25-39` does not expose date. **Path:** `lib/services/register.ts:238-243` uses `new Date().toISOString().slice(0,10)` (UTC), while tenant business date is Asia/Kolkata (`lib/time/tz.ts`, `lib/services/register.ts:63-75` for member join date); downstream session roster filters `enrolments.enrolled_on <= today` (`lib/services/register.ts:354-363`). **Preconditions:** enrolment submitted from 00:00–05:29 IST; occurrence follows directly from UTC-vs-IST conversion; no clock-frozen DB test run. **Impact:** membership may appear as effective from the preceding local day, changing historical roster/report calculations. **Insufficient protection:** DB `date` type stores exactly the wrong default; elsewhere the code uses `todayInZone`. **Evidence:** deterministic arithmetic and source trace; no claim that a specific production row is wrong. **Correction:** derive default from tenant timezone inside transaction, maintain explicit backdated-date validation. **Tests:** fixed clock at IST 00:30 and 23:30, tenant timezone overrides, history/effective roster. **Gates:** L no / D no / P block if retroactive roster accuracy is required (recommended) / R block.

## 15. Investigated false positives

1. **“Parent receipts always 404 because `personId` is not `memberId`” — dismissed.** `issueParentLinkAction` puts `memberId` into the unfortunately named `personId` claim (`lib/actions/parent-link.ts:61-64`); parent view and receipt lookup compare it to `members.id` and `payments.memberId` (`lib/services/parent-view.ts:125-137`, `lib/services/receipts.ts:74-85`). Naming should be corrected deliberately, but valid links are not broken for this reason.
2. **“Two workers necessarily execute each queued job twice” — dismissed.** pg-boss claims jobs under DB locking. Redelivery after a crash and two independently managed stacks remain legitimate idempotency/load risks, not proof of duplicate concurrent claims.
3. **“Five prod advisories mean five exploitable server bugs” — dismissed.** §9 separates build/dev-tool chains and unproven CSS request reachability; patched Next optimizer AVIF advisory is not returned.
4. **“Successful suite means fresh deployment is safe” — dismissed.** H04 fails after one actual fresh deploy and passes after a second because CI explicitly bootstraps twice.
5. **“Local restore proves R2 availability” — dismissed.** No external bucket was contacted; only local dump/restore semantics were exercised.

## 16. Accepted risks and defence in depth

The stateless seven-day parent link has no per-link revocation (`lib/services/parent-link.ts:10-21`): rotating the common secret invalidates every link; settle stolen-link response before sharing live data. Imported consent is the **operator's attestation** backed by their retained external records; the UI cannot independently prove prior guardian approval (`lib/services/member-import.ts:199-237`). The consent rule must be verified by the human controller; this is not a legal finding. Bookings UI is intentionally hidden in reception, while APIs/services exist; accountant shares owner frame; `/parent`/worker is not a real parent UI. Audit/activity partitions have a fixed 2028-12 horizon and require forward migration before 2029. Historical >300-line product modules and the advisory-only line scanner are maintenance debt. Stronger type separation between authenticated staff context and privileged system context, plus AST tests of service-parameter propagation, would defend against H01-like recurrence. No extra DB table is assumed in this recommendation.
